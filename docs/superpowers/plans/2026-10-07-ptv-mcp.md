# PTV MCP Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Cloudflare Worker MCP server exposing `find_stop` and `next_departures` for Melbourne metro trains and trams, guarded by a static query-string token.

**Architecture:** A runtime-agnostic `core/` package holds the PTV client, HMAC signing, caching policy, shaping and the two tool functions. A thin `worker/` package wires them to Workers (`McpAgent`, KV, Cache API, cron, rate limiting). Tools return answer-shaped text, never raw PTV JSON.

**Tech Stack:** TypeScript, npm workspaces, vitest (plain in `core/`, `@cloudflare/vitest-pool-workers` in `worker/`), Cloudflare Workers, `agents` SDK (`McpAgent`), `zod`, Wrangler.

**Spec:** `docs/superpowers/specs/2026-10-07-ptv-mcp-design.md` (refines `SPEC.md`; where they differ the design doc wins).

## Global Constraints

- Metro train (`route_type` 0) and tram (`route_type` 1) only. No buses, no V/Line.
- Two tools only, named exactly `find_stop` and `next_departures`.
- PTV requests are signed HMAC-SHA1 over `path?query&devid=…`, uppercase hex, appended as `&signature=` (see `SPEC.md`, PTV auth).
- `core/` must not import anything Workers- or AWS-specific. It may use `fetch` and `crypto.subtle` globals only.
- Never log, return or put in an error message: a signed PTV URL, `devid`, `PTV_API_KEY` or `MCP_TOKEN`. Never log the query string of an incoming request. Never log tool arguments.
- Times shown to users are `Australia/Melbourne`; UTC internally.
- Live versus scheduled is always labelled: `(live)` when `estimated_departure_utc` is non-null, otherwise `(scheduled)`.
- Cache TTLs: departures 30 s fresh with stale-while-revalidate to 60 s; disruptions 120 s; stop search, routes and directions 24 h; `city_routes` rebuilt daily by cron.
- Missing or wrong `token` query parameter gets HTTP 401 before any MCP or PTV work.
- Secrets: `PTV_DEV_ID`, `PTV_API_KEY`, `MCP_TOKEN`.

## Review Focus

1. A stop query that is empty, whitespace, or contains `/`, `&`, `?` or accents (for example `St Kilda Rd/Domain Rd`) must be URL-encoded safely and must not break the signed path. Task 6 pins it.
2. A stop query with no matches returns a plain "no stops found" message, not an error. Task 6 pins it.
3. A stop with no upcoming services (after last train) returns an explicit "no upcoming services" message. Task 7 pins it.
4. PTV failing (HTTP error, timeout, upstream cap) with nothing cached must produce a short readable error with no URL or `devid` in it; with a cached entry it must return that entry plus the "may be delayed" warning. Tasks 2, 3 and 7 pin it.
5. A departure whose time has just passed shows `0 min`, never a negative number, and `limit` is clamped to 1–10. A Melbourne daylight-saving boundary must still format the right local time. Tasks 4 and 7 pin it.

### Task 3: Cache policy

**Files:**
- Create: `core/src/cache.ts`
- Test: `core/test/cache.test.ts`
- Modify: `core/src/index.ts`

**Interfaces:**
- Produces:
  - `interface CacheEntry<T> { value: T; storedAt: number }` (epoch ms)
  - `interface CacheStore { get<T>(key: string): Promise<CacheEntry<T> | null>; put<T>(key: string, value: T, retainSeconds: number): Promise<void> }`
  - `type CacheSource = "hit" | "stale" | "miss" | "stale-fallback"`
  - `interface Cached<T> { value: T; source: CacheSource; warning?: string }`
  - `interface CacheRuntime { defer(p: Promise<unknown>): void; now(): number }`
  - `interface CachePolicy { freshSeconds: number; staleSeconds: number; retainSeconds: number }`. `staleSeconds` is the end of the stale-while-revalidate window, so departures use `{30, 60, 600}`.
  - `cached<T>(store: CacheStore, key: string, policy: CachePolicy, load: () => Promise<T>, rt: CacheRuntime): Promise<Cached<T>>`
  - `const POLICIES: { departures: CachePolicy; disruptions: CachePolicy; static: CachePolicy }` with departures `{30,60,600}`, disruptions `{120,240,900}`, static `{86400,172800,604800}`.
  - `class MemoryCacheStore implements CacheStore` (exported for tests and local dev).

- [ ] **Step 1: Failing tests** with `MemoryCacheStore` and a fake clock, each asserting `source`, the value, and how many times `load` ran:
  - empty store → `"miss"`, one load, entry stored;
  - age 10 s → `"hit"`, zero loads;
  - age 45 s → `"stale"`, value returned immediately, and a refresh passed to `defer` that updates the store when awaited;
  - age 45 s and the deferred refresh rejects → no unhandled rejection, old entry kept;
  - age 70 s and `load` succeeds → `"miss"`;
  - age 70 s and `load` throws → `"stale-fallback"` with `warning` containing `"may be delayed"`;
  - empty store and `load` throws → the error propagates.

  - `searchStops(client, store, rt, query: string, mode?: Mode): Promise<Cached<StopMatch[]>>`: calls `/v3/search/{encodeURIComponent(query.trim())}?route_types=…`, caches under `search:{normalised term}:{mode|any}` using the static policy, keeps only route types 0 and 1.

  - `ToolContext { client: PtvClient; live: CacheStore; static: CacheStore; rt: CacheRuntime }`, `ToolResult { text: string; cache: CacheSource; isError?: boolean }`.
  - `findStop(ctx: ToolContext, args: { query: string; mode?: Mode }): Promise<ToolResult>`. Text is one line per match: `Ascot Vale Station (train, Ascot Vale) id 1007: Craigieburn line`. An empty or whitespace query returns `isError` with `"Give a stop name to search for."` and makes no PTV call.

### Task 7: `next_departures`

**Files:**
- Modify: `core/src/tools.ts`, `core/src/index.ts`
- Test: `core/test/nextDepartures.test.ts`

**Interfaces:**
- Consumes: `searchStops`, `resolveStop`, `getCityRoutes`, `shapeDepartures`, `renderDeparture`, `shapeDisruptions`, `cached`, `POLICIES`, `ToolContext`.
- Produces: `nextDepartures(ctx: ToolContext, args: { stop: string; mode?: Mode; route?: string; direction?: string; limit?: number }): Promise<ToolResult>`.

Behaviour the implementer must follow:
- `stop` is all digits → treat as a stop ID. The mode comes from `args.mode`; if absent, try train then tram and use the first that returns departures. Otherwise resolve by name with `searchStops` and `resolveStop`; for `many`, return the candidates (same line format as `find_stop`) with `"Which one did you mean?"` and no departures; for `none`, return the Task 6 message.
- Fetch `/v3/departures/route_type/{rt}/stop/{id}` with `max_results=40&expand=Route&expand=Direction&expand=Run`, through `cached` with `POLICIES.departures` under key `dep:{rt}:{stop}:{route|all}`. This differs from the `SPEC.md` key because direction IDs are per route and one stop call covers all routes, so the direction filter is applied after caching and the entries are shared.
- `direction` defaults to `city`. `city` keeps departures where `directionId === cityRoutes[routeId].cityDirectionId`; `outbound` keeps `outboundDirectionIds`; a numeric string keeps that direction ID. A route missing from `cityRoutes` under `city` is skipped, and if that leaves nothing the text says which lines have no resolvable city direction.
- `route` matches a route ID exactly or a case-insensitive substring of the line name.
- `limit` defaults to 5 and is clamped to 1–10.
- Disruptions: fetch `/v3/disruptions?route_types=…&disruption_status=current` (`cached`, `POLICIES.disruptions`, key `dis:{rt}`), keep those whose `routeIds` intersect the returned routes, and append them under a `Disruptions:` heading, at most 3, one line each.
- When `source` is `stale-fallback`, prepend the cache `warning`. `ToolResult.cache` summarises the calls for logging: `miss` if any call went to PTV, else `stale-fallback` if any fell back, else `stale` if any was stale, else `hit`.
- PTV errors with nothing cached → `isError` with `"PTV isn't responding right now. Try again shortly."` and nothing else from the error.
- Header line: `<stop name> (<mode>) toward City:` (or `outbound`, or the direction label).

- [ ] **Step 1: Failing tests** with a fake client serving the fixtures and a fake clock:
  - default call returns only city-bound departures, rendered exactly, with live/scheduled labels;
  - `direction: "outbound"` returns the others;
  - `limit: 0` behaves as 1 and `limit: 99` as 10 (fixture extended to 12 departures);
  - an ambiguous name returns candidates and makes no departures call;
  - a numeric stop ID skips search;
  - after a fresh call, a second call 10 s later makes no further departures request (the "repeat within 30 s" check);
  - empty `departures` → `"No upcoming services at <stop> toward City."`;
  - a disruption on a returned route is listed; one on an unrelated route is not;
  - fetch fails with a stored entry 70 s old → stale text with `"may be delayed"` and `cache` is `stale-fallback`;
  - fetch fails with an empty store → `isError`, text contains neither `devid` nor `signature` nor `timetableapi`.
- [ ] **Step 2: Run; expect FAIL. Implement; run; expect PASS.**
